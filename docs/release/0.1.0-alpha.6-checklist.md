## 7. 压缩阈值实测结论（2026-11-12）

配置：`compaction-basic.thresholdRatio = 0.5`、`summarizationProvider = workbuddy`。

**关键发现：thresholdRatio 在 workbuddy 上不生效。**

宿主 `resolveCompactSpec` 的算法是：

```
messageBudget    = contextWindow - reservedCompletionTokens
pressureBudget   = messageBudget - headroomTokens
thresholdTokens  = floor(min(contextWindow * thresholdRatio, pressureBudget))
```

workbuddy/deepseek-v4.1-flash 实测参数：

| 项 | 值 | 来源 |
| --- | --- | --- |
| contextWindow | 300,000 | session request/context |
| maxTokens（输出预留） | 128,000 | session request/header |
| headroomTokens | 65,536 | compaction-basic 默认 |
| messageBudget | 172,000 | 计算 |
| **pressureBudget** | **106,464** | 计算 |
| **thresholdTokens** | **106,464** | min(300000×0.5=150000, 106464) |

因为 `pressureBudget (106,464) < contextWindow × 0.8 (240,000)`，**阈值 0.8 / 0.5 / 0.4 得到的触发线完全相同**。
真正决定触发线的是 `headroomTokens`，不是 `thresholdRatio`。

历史零压缩的原因不是阈值 0.8，而是：那 6 个会话都在 workbuddy 上跑，触发线一直是 10.6 万，
而它们多数没跑到 10.6 万；跑过的那次（c02d2cf6，2675 KB）需要进一步核对当时的模型路由。

**决定**：先不改 headroomTokens，跑一轮真实会话观察是否真的触发压缩，拿到实际日志再定。
若需要更早触发，正确手段是调小 `headroomTokens`（如 32768 → 触发线 ≈ 7.2 万），而不是调 thresholdRatio。

## 8. 计费边界：Team teammate 不受本插件控制（2026-11-12 二次事故）

### 事故

15:30 后 Lead 为推进 D1 验收，给 `sashi` / `xiaobai` 两个 teammate 发了消息。
这两个会话创建于 15:03/15:04（计费修复 install 之前），descriptor 已固化为：

```json
{"provider":"spawn","agentProvider":"deepseek-account","agentModel":"deepseek-flash"}
```

被唤醒后按 ~300K 旧上下文继续跑，实测造成：

| 会话 | 调用 | input | output | cacheRead |
| --- | --- | --- | --- | --- |
| 小白 e3d88c32 | 16 | 276,819 | 26,652 | 5,772,288 |
| 沙僧 b3098403 | 15 | 31,300 | 18,001 | 10,263,296 |
| **合计** | **31** | **308,119** | **44,653** | **16,035,584** |

### 根因（宿主缺口，非本插件缺陷）

`@deepseek-ai/dsh-experimental-agent-team` 的 spawn 实现：

```js
await this.ctx.subagents.startActivation({
  delivery: "parent", childId, provider: request.provider, label: description,
  request: { prompt: request.prompt, parent: root },   // ← 不传 agentOptions
  signal,
})
```

而 `@deepseek-ai/dsh-subagent` 的 `resolveChildAgentOptions(parent, requested, depth)`：

```js
function parentAgentOptionsForDelegation(parent) {
  const requestConfig = parent.session.requestHeader()?.config
  if (requestConfig === void 0) return { ...parent.options }
  const { provider: _p, model: _m, reasoningEffort: _r, ...createdOptions } = parent.options
  return { ...createdOptions, provider: requestConfig.provider, model: requestConfig.model, ... }
}
```

因为 team 永远不传 `requested`，teammate **必然继承父会话最近一次请求的 provider/model**，
且**在会话创建时固化进 descriptor**，之后改 profile 或重启都不会改变已存在的 teammate。

### 本插件的能力边界

`buildChildAgentOptions()` 只能修复 **`meetingstone_dispatch`** 的派单路径
（那条路径的 request 由本插件组装）。Team teammate 由宿主直接创建，本插件无权干预。

### 结论与纪律

1. **不要为了"省时间"随便唤醒旧的 teammate**。唤醒一个创建于配置修复之前的 teammate，
   等于让它按旧路由继续按量计费。
2. 需要 teammate 协助时，**先确认它的 `agentProvider`**：
   读会话文件里的 `subagent/descriptor` 事件。
3. 已固化 deepseek-account 的 teammate 一律**弃用不唤醒**，需要人手就新建。
4. 重启后新建的 teammate 会继承父会话当时的路由，应验一次 descriptor 再放心使用。
