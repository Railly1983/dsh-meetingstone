## 7. 压缩阈值最终结论（2026-11-12 修订）

配置：`compaction-basic.thresholdRatio = 0.5`、摘要走 `workbuddy/deepseek-v4.1-flash`。

用户随后把 workbuddy 的上下文上限改为 **1,000,000**，实测已生效
（session `request/context` 事件 `contextWindow: 1000000`）。

### 宿主算法

```
messageBudget   = contextWindow - reservedCompletionTokens
pressureBudget  = messageBudget - headroomTokens
thresholdTokens = floor(min(contextWindow * thresholdRatio, pressureBudget))
retainTokens    = floor(messageBudget * retainRatio)
```

（`retainTokens >= thresholdTokens` 时加载即抛错，因此保留比例必须小于阈值。）

### 窗口 30 万时（旧）—— 阈值无效

| 项 | 值 |
| --- | --- |
| contextWindow | 300,000 |
| maxTokens（输出预留） | 128,000 |
| headroomTokens（默认） | 65,536 |
| pressureBudget | 106,464 |
| thresholdTokens | **106,464** |

`pressureBudget (10.6万) < 窗口×0.5 (15万)`，所以 **0.8 / 0.5 / 0.4 触发线完全相同**，
thresholdRatio 形同虚设，真正卡住触发线的是 headroomTokens + 输出预留。

### 窗口改成 100 万后（现在）—— 阈值真正生效

| 项 | 值 |
| --- | --- |
| contextWindow | 1,000,000 |
| maxTokens | 128,000 |
| headroomTokens | 65,536 |
| messageBudget | 872,000 |
| pressureBudget | 806,464 |
| **thresholdTokens** | **500,000（50 万）** |
| retainTokens | 139,520（约 14 万） |

`窗口×0.5 = 50万 < pressureBudget = 80.6万`，取小值 50 万，**正是用户要的 0.5 阈值**。

### 结论

1. 用户把窗口调到 1M 是**必要前提**；否则阈值调到 0.5 也不会生效。
2. 现在触发线 50 万，保留约 14 万，压缩后能剩 14 万上下文继续工作。
3. 若日后想更早触发，正确手段是调小 `headroomTokens`，不是继续调小 thresholdRatio。
4. 注意：`maxTokens = 128,000` 意味着单次输出上限仍按 128K 预留，压缩算的是"消息预算"。

## 8. 计费边界：Team teammate 不受本插件控制（2026-11-12 二次事故）

### 事故

15:30 后 Lead 为推进 D1 验收，给 `sashi` / `xiaobai` 两个 teammate 发了消息。
这两个会话创建于 15:03/15:04（计费修复 install 之前），descriptor 已固化为：

```json
{"provider":"spawn","agentProvider":"deepseek-account","agentModel":"deepseek-flash"}
```

被唤醒后按 ~300K 旧上下文继续跑，实测造成：

| 会话 | 调用 | input | output | cacheRead |
| --- | --- | --- | --- | --- |
| 小白 e3d88c32 | 16 | 276,819 | 26,652 | 5,772,288 |
| 沙僧 b3098403 | 15 | 31,300 | 18,001 | 10,263,296 |
| **合计** | **31** | **308,119** | **44,653** | **16,035,584** |

### 根因（宿主缺口，非本插件缺陷）

`@deepseek-ai/dsh-experimental-agent-team` 的 spawn 实现：

```js
await this.ctx.subagents.startActivation({
  delivery: "parent", childId, provider: request.provider, label: description,
  request: { prompt: request.prompt, parent: root },   // ← 不传 agentOptions
  signal,
})
```

而 `@deepseek-ai/dsh-subagent` 的 `resolveChildAgentOptions(parent, requested, depth)`：

```js
function parentAgentOptionsForDelegation(parent) {
  const requestConfig = parent.session.requestHeader()?.config
  if (requestConfig === void 0) return { ...parent.options }
  const { provider: _p, model: _m, reasoningEffort: _r, ...createdOptions } = parent.options
  return { ...createdOptions, provider: requestConfig.provider, model: requestConfig.model, ... }
}
```

因为 team 永远不传 `requested`，teammate **必然继承父会话最近一次请求的 provider/model**，
且**在会话创建时固化进 descriptor**，之后改 profile 或重启都不会改变已存在的 teammate。

### 本插件的能力边界

`buildChildAgentOptions()` 只能修复 **`meetingstone_dispatch`** 的派单路径
（那条路径的 request 由本插件组装）。Team teammate 由宿主直接创建，本插件无权干预。

### 结论与纪律

1. **不要为了"省时间"随便唤醒旧的 teammate**。唤醒一个创建于配置修复之前的 teammate，
   等于让它按旧路由继续按量计费。
2. 需要 teammate 协助时，**先确认它的 `agentProvider`**：
   读会话文件里的 `subagent/descriptor` 事件。
3. 已固化 deepseek-account 的 teammate 一律**弃用不唤醒**，需要人手就新建。
4. 重启后新建的 teammate 会继承父会话当时的路由，应验一次 descriptor 再放心使用。

## 9. 计费最终验证（2026-11-12 15:44 重启后）

### 事实

| 检查项 | 结果 |
| --- | --- |
| 重启后全机器模型调用 | 2 次 |
| `workbuddy/deepseek-v4.1-flash` | 2 次（100%） |
| `deepseek-account/*` | **0 次** |
| 新建 teammate 探针（5300baf3）descriptor | `agentProvider=workbuddy, agentModel=deepseek-v4.1-flash` |
| 探针实际请求路由 | `workbuddy/deepseek-v4.1-flash` |

### teammate 路由固化规律（已验证）

teammate 的路由在**创建时**由 `parent.session.requestHeader()?.config` 决定，并永久写入 descriptor。
时间线证据：

| 创建时间 | 会话 | 固化路由 | 判定 |
| --- | --- | --- | --- |
| 11:10 ~ 14:02 | 多个 | deepseek-account/deepseek-flash | 配置未修 |
| **14:51:13** | **37b9d2c4** | **workbuddy/deepseek-v4.1-flash** | 父会话当时已是 workbuddy |
| 15:05:40 | c02d2cf6 | deepseek-account/deepseek-flash | 父会话被切回 deepseek |
| 15:39 唤醒 | b3098403 / e3d88c32 | deepseek-account/deepseek-flash | 15:03/15:04 创建，唤醒即按旧路由计费 |
| **15:47 新建** | **5300baf3（探针）** | **workbuddy/deepseek-v4.1-flash** | 修复后正确继承 |

### 结论

1. **新会话的扣费问题已解决**。当前配置下，无论新建 teammate 还是 `meetingstone_dispatch` 派单，
   全部走 `workbuddy`。
2. **存量风险未消除**：磁盘上仍存有 16 个固化为 `deepseek-account` 的旧 subagent 会话。
   它们休眠时不产生费用，但**一旦被唤醒就恢复按量计费**。
   所以准确的表述是「**新会话已解决，存量 16 个仍有唤醒即计费风险**」，
   不能说「扣费问题已彻底解决」—— 后者会诱导人放心唤醒旧 teammate，
   而这正是 2026-11-12 烧掉 31 次调用的同一条路径。
3. 因此纪律是：**永不给创建于 2026-11-12 15:44 之前的 teammate 发消息**。
   需要人手就新建（新建的一定正确）。
4. 若确实需要清理，可考虑删除这些旧会话目录，但会丢失历史记录，不擅自执行。
5. 已知遗留成员（不可删除、不可改名，宿主无 `removeMember`）：
   `sashi`（少一个 g，应为 shaseng）、`route-probe`（临时路由测试）、
   `d1-verifier` / `auditor`（英文名，首次验证 Team 功能时所用）。
