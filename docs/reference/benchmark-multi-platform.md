## 一、实验设计

**固定条件**（全部已实测确认）：

| 项 | 值 | 验证方式 |
|---|---|---|
| 模型（主控 + 子代理） | `deepseek-v4.1-flash` | 桥账本 `model` 字段、CodeBuddy `qua.end` 的 `model` 字段 |
| 思考强度 | `high` | 桥请求 `reasoning.effort`、CLI `--effort high` |
| 协作形态 | 1 主控拆解 → 4 子代理各领 1 子任务 → 主控汇总 | 每格都是完整任务，不是孤立单次调用 |
| 任务 | `L=[17,5,23,8,31,12,40]` 求 `sum/gt20/max/maxPos` → 严格 JSON | 真值 `{sum:136, gt20:3, max:40, maxPos:7}` |
| 矩阵 | 4 方案 × 4 槽位 × 3 重复 = **48 格** | 12 次完整协作任务 |

**四方案的真实机制**（这是差异的来源，不是同一件事的四个壳）：

| 方案 | 主控 | 子代理机制 | 模型接入路径 |
|---|---|---|---|
| a | DSH 会话 | 集合石 `meetingstone_dispatch`，`acp-cli` | 启动 CodeBuddy CLI（`--acp --model`），**走 CodeBuddy 自有认证，不经 WorkBuddy 桥** |
| b | DSH 会话 | 官方 `subagent`（`spawn`，in-process） | WorkBuddy 桥 adapter |
| c | 脚本直调 | 桥 `/v1/chat/completions` | WorkBuddy 桥 |
| d | Codex CLI | 桥 `/v1/responses`（隔离 `CODEX_HOME`） | WorkBuddy 桥 |

## 二、48 格结果

| 方案 | 任务数 | 平均墙钟 | 子代理正确 | 平均汇总 | 子代理 token/格 | 子代理 credit/格 | 主控 token/任务 | 主控 credit/任务 |
|---|---|---|---|---|---|---|---|---|
| **a** 集合石 ACP | 3 | **13.3s** | **12/12** | **5/5** | 953 | 不可测（不走桥） | 不可分离 | 不可测 |
| **b** 官方 subagent | 3 | ~24.5s（窗口跨度） | 11/12 | 4.67/5 | **16,275** | 0.044 | **183,498** | **0.515** |
| **c** 桥直调 | 3 | **4.8s** | 11/12 | 4.67/5 | **63** | 0.000 | **476** | 0.040 |
| **d** Codex CLI | 3 | 47.5s | **12/12** | **5/5** | 219 | 不可测（CLI 不回报） | 678 | 0 |

**全量消耗**：子代理 210,113 tokens / 0.53 分；主控 553,956 tokens / 1.67 分。

### 唯一的质量差异（真实错误，非判分 bug）

- **b rep3 slot4**：答 `maxPos:6`（应为 7）—— 这是真实错误。
- **c rep2 slot2**：答错 `gt20`，同样是真实错误。
- a 和 d 的 12 格全对。

同一个模型、同一个任务，错误率 ~2/48 ≈ 4%，说明**差异主要来自调度链路而非模型能力**。

## 二之二、四方案 token 消耗对比（统一口径）

> 上一版表格混了口径（有的按格、有的按任务，还有几个"不可测"），无法横向比较。这里统一重算。
> 脚本：`.token-test/token-comparison.mjs`、`token-split.mjs`；数据 `.token-test/token-comparison.json`。

### 口径①：子代理每格 token —— 唯一干净可比的口径

同一任务、同一模型（`deepseek-v4.1-flash`）、同一思考强度（`high`），只差调度机制：

| 方案 | 子代理 token/格 | 相对 c | 差异来源 |
|---|---|---|---|
| **c** 桥直调 | **63** | 1× | 只发任务本身（约 60 token） |
| **d** Codex CLI | **219** | 3.5× | Codex 每次 exec 附带系统提示与工具定义 |
| **a** 集合石 ACP | **953** | 15.1× | CodeBuddy CLI 的 ACP 会话初始化开销 |
| **b** 官方 subagent | **16,275** | **258×** | in-process `spawn` 每格携带完整 spawn 系统提示 |

**这是最该看的一列**：同为"把一句 60 token 的任务发给子代理并取回答案"，b 比 c 多烧 **258 倍**。

### 口径②：一次完整协作任务（1 主控 × 2 次调用 + 4 子代理）

| 方案 | 主控/任务 | 4 子代理/任务 | **单任务合计** | 48 格全量 |
|---|---|---|---|---|
| a 集合石 ACP | 366,996 | 3,812 | **370,808** | 1,112,424 |
| b 官方 subagent | 366,996 | 65,100 | **432,096** | 1,296,288 |
| c 桥直调 | 476 | 252 | **728** | 2,184 |
| d Codex CLI | 678 | 876 | **1,554** | 4,662 |

### 关键：这 500 倍差距主要不是调度方式，而是主控上下文大小

a/b 的主控就是**当前这个已跑了约 180K 上下文的 DSH 会话**；c/d 的主控是**全新启动、上下文几百 token 的脚本**。
b 实测主控单次 = prompt 183,028 + out 470，其中**会话上下文占 99.7%**，真正新增的计算很小。

若把主控归一化到同一上下文规模（~5K），差距立刻收敛：

| 方案 | 主控/任务 | 4 子代理/任务 | 单任务合计 | 相对 |
|---|---|---|---|---|
| a 集合石 ACP | 10,940 | 3,812 | 14,752 | 1.3× |
| b 官方 subagent | 10,940 | 65,100 | 76,040 | **6.8×** |
| c 桥直调 | 10,940 | 252 | 11,192 | 1.0× |
| d Codex CLI | 10,940 | 876 | 11,816 | 1.1× |

**结论**：调度机制的真实差距是 **b 约为 c 的 6.8 倍**（其余三者几乎持平）；此前看到的 500 倍是主控长会话放大的结果。

### 口径③：WorkBuddy 积分（钱）

| 方案 | 子代理 分/格 | 主控 分/任务 | **单任务合计** | 说明 |
|---|---|---|---|---|
| a 集合石 ACP | 0（走 CodeBuddy 额度） | 0 | **0** | 消耗记在 CodeBuddy，不进 WorkBuddy 积分 |
| b 官方 subagent | 0.044 | 0.515 × 2 | **1.206 分** | 最贵 |
| c 桥直调 | 0.000 | 0.020 × 2 | **0.040 分** | 最省 |
| d Codex CLI | 不可测 | 未回报 credit | **不可测** | 桥不回 credit，只能拿 token |

### 主控 vs 子代理 谁在烧 token

| 方案 | 主控占比 | 子代理占比 |
|---|---|---|
| a | 99% | 1% |
| b | 85% | 15% |
| c | 65% | 35% |
| d | 44% | 56% |

→ **a/b 的 token 几乎全烧在主控（长会话）上，不在子代理分发上**。这直接解释了你之前"2000 积分消耗太快"的观感。

## 三、三个决定性发现

### 3.1 你说的"DSH 子代理不支持多模型混跑"——实测确认，而且比预期更深

显式指定非父路由模型直接被拒：

```
child LLM route "workbuddy/deepseek-v4.1-flash" is not allowed for this Session;
without a recorded model-selection policy, explicit selection (including reasoning_effort)
is limited to the parent route
```

`hy3`、`deepseek-v4.1-flash` 全被拒，只有与父路由相同的模型放行。**并且改 `agent-default-model` 不影响已创建的会话**——我把配置改成 deepseek 后，当前会话仍锁在 hy4free，直到会话模型真正切换过来，b 方案才跑通。这是 DSH 的设计，不是配置错误。

### 3.2 b 方案最贵，贵在 in-process 子代理每次重放完整系统提示

| 指标 | b | c | 倍数 |
|---|---|---|---|
| 子代理 token/格 | 16,275 | 63 | **258×** |
| 主控 token/任务 | 183,498 | 476 | **385×** |
| 子代理 credit/格 | 0.044 | 0.000 | — |
| 主控 credit/任务 | 0.515 | 0.040 | 13× |

原因：in-process `spawn` 子代理每格都携带完整的 spawn 系统提示（约 16K），而桥直调只发任务本身（约 60 token）。**b 的成本结构是"每格固定 16K 起步"**，格子越多越吃亏。用户此前担心的"token 消耗非常大"，在 b 上就是这个机制。

### 3.3 a 方案根本不在 WorkBuddy 积分体系里

集合石 ACP 启动的是 `codebuddy` CLI，日志 `qua.end` 显示它用 CodeBuddy 自有认证（`userId c28ba596…`）。它的 token 精确可测（`prompt_tokens`/`completion_tokens`/`total_cost_ms`），但**消耗记在 CodeBuddy 额度，不是 WorkBuddy 积分**。四种方案的成本不能简单相加比较——这是口径差异，必须在报告里说清。

## 四、token 可测性（用户最关心的维度）

| 方案 | 子代理 token 来源 | 可测性 |
|---|---|---|
| a | CodeBuddy CLI `qua.end`（按 operationId 精确归因到每次派单） | ✅ 精确 |
| b | 桥账本 `usage.jsonl`（按 prompt 规模区分主控/子代理） | ✅ 精确 |
| c | 桥响应 `usage` 字段 | ✅ 精确 |
| d | Codex CLI 自报 `tokens used`（仅总数） | ⚠️ 只有总数，无 prompt/completion 拆分 |

**顺带纠正一个此前的判断**：免费模型并非"测不出 token"。`hy4free` 在桥账本有 233 条记录、25.48M token，`credit=0` 但 token 完整。换 deepseek 的理由应该是"要统一模型做干净对照"，而不是"免费模型测不出 token"。

## 五、结论与建议

按用户三个维度排序：

| 维度 | 最优 | 最差 | 说明 |
|---|---|---|---|
| **速度** | c（4.8s） | d（47.5s） | d 慢 10 倍，因为每次 `codex exec` 要冷启动整个 CLI |
| **成本** | c（0.04 分/任务） | b（0.56 分/任务） | b 贵 14 倍，固定 16K 系统提示开销 |
| **质量** | a / d（12/12, 5/5） | b / c（11/12, 4.67） | 差异是随机的，不足以判定优劣 |
| **可测性** | a / b / c | d | d 只有总 token |

**给实际使用的建议**：

1. **日常主力用 c 的路由（桥直调）**：最快、最省、token 完全透明。若需要多步工具调用，用 DSH 原生 agent 但**避免 b 的 in-process spawn 高频派单**。
2. **需要长任务与严格验收时用 a（集合石 ACP）**：质量最稳，但成本记在 CodeBuddy 额度，要单独盯那边的用量。
3. **d（Codex）只适合验证协议兼容性**，不适合当日常调度：47.5 秒/任务里有 90% 是 CLI 冷启动。
4. **b（官方 subagent）慎用于批量任务**：每格 16K 固定开销在 48 格上就是 78 万 token。

## 六、尚未解决 / 需注意

1. **b 的墙钟不可精确到单任务**：4 子代理并行派发、异步消息返回，只能给出窗口跨度 24.5s，标注为不可比。
2. **a/b 的主控 token 不可分离**：主控就是当前 DSH 会话，其调用混在会话长上下文中。b 用桥账本按 prompt 规模（≥100K 判为主控）近似；a 完全无法分离，标为 null。
3. **d 的 credit 恒为 0**：Codex CLI 走桥但桥不回 `credit` 字段，只能拿 Codex 自报 token。
4. **48 格单次重复样本偏小**：每个方案仅 3 次重复，质量差异（11/12 vs 12/12）不具统计显著性，结论应以速度和成本为主。
