## 3. 产品形态与最小架构

### 3.1 一句话定义

一个装在 DSH 里的**薄层插件**：维护“角色 → 执行通道（CLI/Provider/模型/强度/权限）”的映射，让用户用自然语言（“让沙僧把这个模块重构了”）把任务派发到正确的 CLI，执行过程、任务状态、用量统计全部留在 DSH 原生体系里。

### 3.2 架构图（第一版）

```
DeepSeek Harness Host  ← 全部复用，不改一行核心代码
  ├─ Plugin Manager / Settings        ← 插件安装、启停、配置界面
  ├─ Workspace / Project              ← 项目目录、项目归属
  ├─ Subagent / Providers             ← 真正的任务执行与生命周期
  ├─ Jobs / Todo / Session            ← 任务状态、日志、可回溯
  ├─ Token Meter / Permissions / Sandbox
  └─ meetingstone（本项目插件）
       ├─ Role Registry              角色 + 别名 + 冲突校验
       ├─ Project Config              .meetingstone.json 读取/合并/收紧
       ├─ Capability Query           向宿主 Provider 查真实模型/强度枚举
       ├─ CLI Health Check           仅补“本机可执行文件/版本”这一真实缺口
       ├─ Dispatch Tool              解析角色 → 校验 → 调宿主 Subagent
       └─ Minimal Settings UI        角色 CRUD + 健康状态 + 派单备注
```

设计红线（继承交接文档）：

1. 不自研任务队列/生命周期 → 一律返回宿主 task/session 引用。
2. 不自建数据库 → 全局配置进 DSH Settings，项目配置进 `.meetingstone.json`。
3. 不重写 Persona/Preset/Skills → 角色只做“通道映射”，职责描述作为 Prompt 前缀注入。
4. 只写“宿主确实缺”的那一层：**本机 CLI 可执行文件探测**（宿主 Provider 只知道自己能不能跑，不告诉你本机装没装、版本多少）。
5. 不具备的能力（如某 CLI 无法真只读）显示“无保证”，不假装支持。

## 7. 阶段 2：角色映射与派单（P2）

### 7.1 角色数据模型（草案，最终由 P0-07 定稿）

```jsonc
{
  "roleId": "role-sashi",          // 稳定 ID，^role-[a-z0-9][a-z0-9-]*$，改名不变
  "name": "沙僧",
  "aliases": ["SS", "主力执行"],    // 跨角色全局唯一（大小写不敏感、去空白），冲突拒绝保存
  "description": "主力开发和批量执行",
  "channel": {
    "kind": "external-cli",         // external-cli（本机 CLI：codex / codebuddy / claude）| dsh-subagent（DSH 原生子 Agent）
    "provider": "codex-cli",        // external-cli 时必填：宿主可用的 Provider / CLI 标识
    "cli": "codex",                 // 本机平台标识
    "model": "<由能力查询返回>",     // 必须来自真实能力列表
    "reasoning": "high"             // 必须是该模型实际支持的枚举值
  },
  "permissionPreset": "project-write",  // read-only | project-write | restricted | approval
  "enabled": true,
  "fallbackRoleId": null,           // 第一版只提示，不自动接替
  "timeoutMs": 1800000
}
```

项目文件 `.meetingstone.json`（草案）：

```jsonc
{
  "version": 1,
  "defaultRoleId": "role-sashi",
  "roles": [],                       // 项目级新增角色
  "roleOverrides": {                 // 只允许收紧，不允许放宽
    "role-sashi": { "model": "...", "reasoning": "medium", "permissionPreset": "read-only" }
  },
  "dispatchNotes": "常规实现优先交给沙僧；关键修改完成后交悟空复核。",
  "projectRules": ["未经确认不得修改数据库迁移文件"],
  "limits": { "maxParallelReadonly": 3, "serializeWrites": true }
}
```

**合并规则**：`项目 > 全局`；`permissionPreset` 只能收紧不能放宽（`read-only` 最严 → `approval` 最松），越权放宽直接拒绝并报错。

### 7.2 工具接口（草案）

| 工具 | 入参 | 返回 | 错误码 |
| --- | --- | --- | --- |
| `meetingstone_list_roles` | `{}` | 角色数组：`roleId/name/aliases/provider/cli/model/reasoning/permissionPreset/enabled/availability{providerReady,cliInstalled,modelSupported}/source(global\|project)` | — |
| `meetingstone_dispatch` | `{ role, task, context?, readOnly?, timeoutMs? }` | `{ taskRef:{providerTaskId,sessionId?}, role, resolvedProvider, permissionPreset, startedAt }` | `ROLE_NOT_FOUND` `ROLE_DISABLED` `PROVIDER_UNAVAILABLE` `MODEL_UNSUPPORTED` `PERMISSION_ESCALATION_DENIED` `WRITE_CONFLICT` `PATH_OUTSIDE_PROJECT` |

| `meetingstone_cancel_task` | `{ taskRef }` | 代理宿主原生取消结果 + 子进程是否已退出 | `CANCEL_FAILED` |
| `meetingstone_cli_status` | `{ cli? }` | 每 CLI：`installed/path/version/auth(known\|unknown)/handshake/checkedAt/source`；**不返回余额** | — |

## 10. 权限与安全设计（第一版）

| 档位 | DSH 侧手段 | CLI 侧手段 | 若做不到 |
| --- | --- | --- | --- |
| 只读 | 只读模式 / 审批关闭写入 | CLI 原生只读/plan 参数 | 明确标注“无只读保证”，不得标记安全只读（CodeBuddy 即属此类待验证项） |
| 项目写入 | 工作目录限制 + 审批 | CLI `--cwd`/工作目录参数 | 标注“仅提示性限制” |
| 受限命令 | 审批白名单 | CLI 原生命令白名单 | 若宿主与 CLI 都无白名单 → 降级为“人工批准” |
| 人工批准 | 宿主审批机制 | 不适用 | — |

硬性约束（写进代码，不靠 Prompt）：

1. 派发目标目录必须在当前项目根之内，否则拒绝。
2. 不读取、不复制、不注入其他 CLI 的登录凭据。
3. 环境变量白名单传递。
4. DSH 退出/插件卸载时清理子进程与句柄。

## 12. 团队分工与派发策略

> 注意区分：**本节是“我们自己怎么分工”**（开发期团队编制），第 7 节是“插件要实现的角色注册表”（产品功能）。两者概念同源，但不是同一个东西。

### 12.1 团队编制（已确认）

| 角色 | 执行通道 | 模型 / 强度 | 定位 | 额度纪律 |
| --- | --- | --- | --- | --- |
| **唐僧** | Codex CLI | `gpt-6-astra` / `high` | 团队领导：架构、战略、关键决策、最终质量把关 | 能力最强但额度有限，**只用于最重要的决策与验收** |
| **悟空** | Codex CLI | `gpt-6.1-sol` / `high` | 核心资深专家：疑难问题、审核验收、长时间 Agent 任务 | 额度也有限，**高难任务才给他** |
| **八戒** | DSH 原生（本会话，即我） | `deepseek-flash-4.1` / `high` | 技术主管：调度、监工、整合、全能兜底 | 默认不抢主力活，但保证链路不断 |
| **沙僧** | CodeBuddy CLI | `deepseek-v4.1-flash` / `high` | 技术骨干：主力干活 | 干活主力之一（纯文本模型，快且质量稳） |
| **小白** | CodeBuddy CLI | `hy4free`（Hy4 免费档） / `high` | 牛马：主力干活、打杂 | 干活主力之二（杂活全能型） |
| （可选）Claude Code 审核员 | Claude Code CLI | — | 独立架构审查 | 当前未安装，按需补装 |

### 12.2 派发方式（不再“我自己干”）

开发任务通过本机已安装的 **CLIWorker**（`dsh-cliworker-now@0.8.7`）派发给 Codex / CodeBuddy Worker，Worker 在隔离副本里干活，我负责核查与合回。具体做法：

| 环节 | 做法 |
| --- | --- |
| 开新任务 | `cliworker_start`，显式给 `cli`（`codex` / `codebuddy`）与 `agent_name`（`tangtang` / `wukong` / `shaseng` / `xiaobai`）；模型与强度在插件弹窗里按 12.1 选择 |
| 续聊 | `cliworker_followup`，按 `agent_name` 续，保留上下文与角色快照 |
| 只读评审 | Codex 走原生 read-only/plan 模式；评审类任务一律只读，不允许改文件 |
| 写码任务 | 每个 Worker 的文件域必须互不重叠（例：沙僧写 `src/roles/**`，小白写 `src/ui/**` + `docs/**`），由我在主干统一核验后合回 |
| 进度 | `cliworker_status` 只读查询，不轮询；完成通知到达后我读输出并核验实际改动 |
| 兜底 | 若无合适 Worker（额度耗尽 / CLI 异常），才由我自己动手，并在任务清单标注原因 |

**Clean-room 边界**：CLIWorker 只作为**开发期工具**使用（帮我们调用外部 CLI），不进入产品代码、不成为产品依赖、不复制其任何实现。`docs/CLEAN_ROOM.md` 会写明这条。

### 12.3 任务 → 角色映射（默认派发规则）

| 任务性质 | 默认给谁 | 复核 |
| --- | --- | --- |
| 环境/接口/源码取证、能力矩阵 | 沙僧、小白（可并行） | 悟空抽查关键结论 |
| 插件骨架、构建链、类型与 lint 修复 | 沙僧 | 八戒验收 |
| 设置页 UI、文档、CHANGELOG | 小白 | 八戒验收 |
| 角色注册表、配置合并、派单核心（关键路径） | 沙僧 + 八戒配对 | 悟空独立复核 |
| 疑难问题（宿主 API 不明、打包失败、行为异常） | 悟空 | 唐僧（仅当影响架构） |
| 架构取舍、阶段 Gate 签署建议、发布前终审 | 唐僧 | — |
| CI、测试用例补充 | 小白 | 沙僧交叉跑一遍 |

### 12.4 协作纪律

- 审计类只读任务可并行；写代码任务同一时刻只有一个写者（对应交接文档 6.4“同项目写任务默认串行”）。
- 交接只传“背景 + 目标 + 相关文件 + 前序结论 + 遗留问题 + 验收要求”，不传全部聊天历史。
- 任何 Agent 的结论都必须带证据；复核者不得照抄上游结论（这是悟空的明确职责）。
- 每个任务完成后，我在任务清单里更新状态并写明“谁做的、证据在哪”。

## 13. 风险登记册

| 编号 | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 商店应用形态的 CLI 路径随版本升级整体漂移（Codex 已踩到：`26.1103.4239.0` → `26.1103.7773.0`）；且用户机器上未必四个 CLI 齐全（Claude 当前未安装） | 写死路径的健康检测上线即失效；“四平台”承诺落空 | 健康检测按“PATH → Appx 包解析 → npm 全局 → 常见目录 → 手工指定”多源解析，运行时解析不写死、缓存带失效；缺失时如实显示“未安装/未验证”，兼容矩阵标注已实测范围 |
| R2 | 官方 Provider 可能使用平台托管运行时/SDK，而非本机 CLI | “角色 = 某个本机 CLI”这个产品心智可能与实际执行路径不一致 | 角色模型区分 `provider`（执行通道）与 `cli`（本机平台标识）；UI 明示“执行通道 / 是否本机 CLI”，不混淆 |
| R9 | 多个 Worker 并行改同一仓库产生合并冲突（隔离副本合回） | 返工、覆盖别人改动 | 派发前按文件域切分（互不重叠）；只读评审不占文件域；由我统一核验后合回，冲突按目标整合而不是二选一 |
| R10 | 唐僧/悟空额度耗尽（能力最强但额度有限） | 关键节点无人把关 | 高难任务优先悟空、卡住再升唐僧；额度见底时降级到沙僧/小白 + 我自己复核，并在任务清单标注“未走最高档复核” |
| R3 | Agent Teams 为 Experimental，一次性 Subagent 可能无法成为 Team 成员 | 若第一版承诺 Team 集成，可能做不出来 | 第一版执行通道锁定 `subagent`；Team 仅作为 P0-05 结论后的可选增强 |
| R4 | 父 Agent 沙箱未必约束外部 CLI 子进程 | 权限档位可能无法真正落实，宣传即有安全风险 | P0-08 实测；做不到就降级展示并写进安全文档 |
| R5 | 与已安装的 `dsh-cliworker-now` 功能重叠、易被质疑抄袭 | 开源信誉风险 | 工具前缀/配置键/数据结构全部独立命名；`docs/CLEAN_ROOM.md` 记录审查流程；README 明确差异与独立性 |
| R6 | DSH 为 nightly 通道，宿主协议/插件 API 漂移 | 装完就废 | 锁定 peer 版本范围；P0 与 P4 各核验一次；`docs/compatibility.md` 维护兼容矩阵 |
| R7 | `meetingstone` 名称在 GitHub/npm 被占用 | 发布卡点 | P0-09 预先核验，准备 3 个备用名 |
| R8 | 一次性派单超时/断连后子进程残留 | 资源泄漏、文件半改 | 取消即校验进程树；重试前先检查文件是否已部分修改 |
