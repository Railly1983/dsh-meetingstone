# 典型应用场景

这些例子说明如何组织不同 CLI 的角色，而不是保证一句自然语言指令能自动完成所有后续环节。每次实际派单仍由 DSH 判断并调用工具。

## 场景一：便宜的模型干活，强模型把关

- 「让执行者实现用户列表的分页接口，完成后提供测试结果。」
- 等完成后：「让审查员独立检查本次改动，重点看权限、边界条件和回归风险。」

**价值**：不必每项普通工作都使用最贵的模型；重要变更可以用另一个模型独立复核。审核是第二次独立派单，会有额外用量。

## 场景二：让熟悉不同工具的 CLI 各尽其能

- 「让 CodeBuddy 角色定位这个前端组件的报错原因。」
- 「让 Codex 角色审查服务端并发设计，给出最小修复建议。」

**价值**：保留各 CLI 的原生能力和登录方式，DSH 负责组织指令，集合石负责角色到执行通道的映射。可用模型和权限取决于实际 Provider。

## 场景三：并行处理两个独立模块

- 一个执行实例负责报表导出，另一个负责通知模板。
- 仅在文件写入范围不重叠时允许并行；启用 Git worktree，分别完成并验证，再人工检查合并。

**价值**：真正独立的任务有机会缩短总耗时。**代价**：多实例重复初始化、阅读文件和模型上下文，可能比串行消耗更多 Token。

## 场景四：让调度会话保持轻量

- 执行者在自己的 CLI 中读取代码、运行测试、解决问题。
- DSH 只获取结论、改动文件、测试证据和后续行动。

**价值**：不需要把执行日志全部带回 DSH 主会话，有利于控制上下文膨胀。但提示词缓存仍由模型服务端管理，插件不能保证跨模型共享缓存。

## 不适合的情况

- 只有一个 CLI，而且 DSH 原生子代理已经能很好完成任务。
- 希望自动跨 CLI 共用完整隐藏推理或 KV Cache。
- 期望插件取代自动项目管理、任务编排、权限沙箱或 Git 合并工具。
