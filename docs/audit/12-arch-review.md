## 5. 复核暴露的产品级问题（需负责人裁决，记为 DD7）

**官方 `SubagentActivationSpec` 没有 model / reasoning 字段**，所以「角色 → 模型/强度」这条**无法在派单时生效**。

当前实现选择：角色一旦写了 `model` 就**拒绝派单**（fail-closed，宁可报错不静默忽略）。但这意味着第一版的核心卖点之一暂时不可用。

三条出路（需要定）：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 角色 `model` 降级为**声明性元数据**（只展示、不传递），派单不因此被拒 | 与"配置即生效"的直觉冲突，必须在 UI/文档里说明白 |
| B | 用 **provider 行**承载模型（如 acp 的 `command` 带 `--model`），角色只负责选通道；校验角色声明与通道声明一致 | 需要用户为每个模型配一个 provider 行，配置变重 |
| C | 自研一层把模型映射进 CLI 参数 | 违反"不自研启动器"红线，否决 |

**当前状态：按 B 的方向预留（角色 model 与通道声明比对），A 作为兜底；等真机联调确认 provider 行能否读回配置后再定稿。**

## 6. DD7 已决（2026-11-10，负责人选择方案 B）

- 插件配置新增 **`channels`（通道实例表）**：一行 = 一个已配置的 provider，模型/强度写在实例上。
- 角色通过 `channel.channelId` 引用实例，并声明期望的 `model`/`reasoning`。
- 派单时校验「角色声明 == 实例配置」：不一致 → `MODEL_UNSUPPORTED` 并给出双方取值；引用不存在的实例 → 同样拒绝。
- 已实现 + 3 项测试（一致通过 / 不一致拒绝 / 实例不存在拒绝）。
