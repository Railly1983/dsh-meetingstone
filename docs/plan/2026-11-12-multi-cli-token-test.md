## 0. 结论先行（TL;DR）

1. **小任务不要拆并行。** 同一角色开多实例，在 1 分钟级小任务上只省 17% 墙钟，却多烧 23% 输入 token、74% 未命中 token；DSH 原生子代理的对照更极端：多烧 79% token，墙钟几乎没省（-10%）。
2. **默认架构应保持"单协调者 + 单执行实例串行"**；并行只在「任务独立 + 单任务 ≥2~5 分钟 + 独立 worktree」时显式开启，上限 2~3 个。
3. **交接要用"6 字段结构化 + 证据片段内联"，不要传完整聊天历史。** 完整历史让累计输入 +21%，且两组接收者都还是回去重读了源文件——真正决定交接成本的是"是否必须重读项目"，不是交接物长短。
4. **Prompt Cache 的关键在系统提示/角色提示这一层（本项目实测稳定前缀 ≈ 11.7K tokens）**：固定前缀第二发只重付 211 个未命中 token；把动态任务 ID/时间放到固定内容前面，固定块（≈1.2K）就每次全额重付。但注意：在 CodeBuddy 这类 25K 系统提示的 CLI 里，交接物 1~6KB 的差异只占总价 1~5%。
5. **命中率不是成本指标。** 协调者会话累计 5.9M token 中 97.8% 是缓存命中，但那是"每步重发上下文"的累计处理量，不是账单。
6. **Codex 全链路本次不可执行**（无额度），已按规则标「未知」，没有用推测填充；替代验证用 CodeBuddy + DSH 同构完成。
7. **官方 Agent Teams 与 MeetingStone 不冲突、可组合**：官方团队负责协作面（成员/任务板/邮箱/UI），MeetingStone 负责跨 CLI 执行面；官方成员可以直接调用 `meetingstone_dispatch`。详见 `docs/plan/2026-11-12-agent-team-fit.md`。

## 2. 测量口径

### DSH 侧
- 源：`~/.dsh/sessions/<workspace>/<sessionId>/session.v4.jsonl.zstd`（多帧 zstd 逐帧解压）
- 四桶：`uncachedInput / output / cacheRead / cacheWrite`；命中率 = `cacheRead / (cacheRead + uncachedInput)`
- 同一 `(turn,step)` 替换、`llm/retry-started` 后重计（与宿主 `dsh-token-meter` 口径一致）

### CodeBuddy 侧
- 源：`~/.codebuddy/projects/<project-dir>/<sessionId>.jsonl`
- 每 API 调用一条 `providerData.rawUsage`：`prompt_tokens`（总）/ `completion_tokens` / `prompt_tokens_details.cached_tokens`（命中）
- 未命中 = `prompt - cached`；命中率 = `cached / prompt`

### 不可得（写「未知」，不推算）
- Codex usage（无额度，无数据）
- 金额：本机无价目表，四桶未乘单价 → 全部标「金额未知」
- 跨供应商横向比较：模型 ID 不同（deepseek-flash / deepseek-v4.1-flash / hy3），**不做原始 token 横比**

## 4. 测试二 · 同一角色多实例（沙僧）

任务：两个只读分析任务（`src/result-contract.js`、`src/cli/preflight.js`），同角色、同模型、同 effort、同项目快照、各自独立 worktree。

| 组 | 形态 | 墙钟 | 请求数 | 输入·未命中 | 输入·缓存命中 | 输出 | 命中率 | 验收 |

## 5. 测试三 · 交接效率（沙僧 → 小白）

阶段 1（沙僧）：只读分析 `src/context-replay.js`，输出三段报告（6,446 字节完整原文）。
阶段 2（小白，两个独立 worktree）：

| 组 | 交接物 | 墙钟 | 请求数 | 输入·未命中 | 输入·缓存命中 | 输出 | 首请求 prompt | 是否重读源文件 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A | 完整原文（≈6.4KB 全过程+证据） | 42.9s | 5 | 58,557 | 97,216 | 2,397 | 25,955 | 是 |
| B | 6 字段结构化简报（≈1.2KB） | 86.2s | 4 | 60,846 | 67,840 | 4,751 | 25,822 | 是 |

- 累计输入：A 155,773 vs B 128,686 → **完整历史多 21.1%**（差异主要来自 A 每次请求多背整段原文）
- 首请求 prompt：A 25,955 vs B 25,822 → **几乎相同**（CodeBuddy 系统提示+工具定义占绝对大头）
- **两组接收者都回去读了源文件**，所以"精简交接"并没有省掉重读成本
- 质量：结论都命中同一核心问题（L378/L257 的 `unknown` 语义冲突）；B 额外纠正了交接里"title/goal 越界"的误判（读码后确认是设计意图）→ 质量略优
- 上下文遗漏：无关键事实丢失；返工次数 0

**结论**：
1. 完整历史 ≠ 完整上下文。真正要共享的是事实/决策/证据/产物位置。
2. 在外部 CLI 里，系统提示（25~26K）才是成本主体；交接物长短影响 <5%。
3. 要真正省掉"重读"，结构化交接必须**内联证据片段**（`file:line` + 原文 ≤5 行），而不能只给"结论+行号"——只给行号等于要求接收者自己再读一遍。

## 6. 测试四 · Prompt Cache 命中率（DeepSeek API，真实缓存统计）

### 6.1 实验 1：短公共上下文（≈20 token）
| 组 | 第 1 次（冷）未命中 | 第 2 次未命中 | 缓存读 |
| --- | --- | --- | --- |
| A 稳定前缀（同一提示词） | 1,118 | **222** | 12,672 |
| B 动态前缀（前置随机 ID+时间） | 1,171 | **1,171** | 11,776 |

### 6.2 实验 2：长公共上下文（≈1.2K token 固定项目规范）
| 组 | 第 1 次未命中 | 第 2 次未命中 | 说明 |
| --- | --- | --- | --- |
| C 稳定前缀 | 1,363 | **211**（-84.5%） | 固定块第 2 次全部命中 |
| D 动态前缀 | 1,417 | **1,416**（0%） | 固定块每次全额重付 |

- **系统提示缓存基线恒为 11,776 tokens**：只要角色/系统提示/工具定义不变，这部分几乎永久命中（命中率 89%~98%）。
- 动态内容放在固定内容之前 → 固定块从"命中"变成"每次未命中"（本例 +1,205 token/次）。
- 预热效应：冷启动首请求 ≈12.5K 未命中，预热后 ≈1.2K；**每组第一次请求必须单独看，不能当架构缺陷**。

### 6.3 同一 CLI 多实例（C 组）
沙僧双实例：每个实例第 1 次请求都付 ≈22K 未命中（系统提示冷启动），彼此不共享首请求缓存；第 2 次起各自命中自己的前缀（≈26K）。→ 多实例不共享缓存收益，反而各付一次入场费。

### 6.4 跨 CLI（D 组）· 不可比
DSH=`deepseek-flash`、沙僧=`deepseek-v4.1-flash`、小白=`hy3`，模型/服务端不同，缓存键空间不同 → **不测、不横比，标「不可比」**。CodeBuddy 侧观测到首次请求有 ≈3,328（沙僧）/≈512（小白）的缓存基线，但无法证明与 DSH 请求复用。

**结论**：稳定前缀的收益是"消灭重复的固定开销"，不是"提升命中率数字"。命中率 99% 的长会话累计 5.9M token，但其中 97.8% 是缓存读——命中率高≠总成本低。

## 8. 架构裁决（逐条回答任务书八问）

1. **Codex 原生子代理 vs 独立线程，哪个更适合插件？**
   本次无法实测 Codex（无额度），**不裁决**。同构证据（DSH 原生子代理）显示：小任务并行 +79% token、几乎不省时间。→ 默认策略：**不自动并行**，并行需显式开关。

2. **CodeBuddy 是否也应优先用原生子代理？**
   不优先。CodeBuddy 确实原生支持子代理（`--subagent-permission-mode`），但 ACP 一次性派单下**不可观测、不可归因、不可控**。要用就用"独立实例 + worktree"，可控且能出账。

3. **哪些场景必须用独立 CLI 线程？**
   ① 长任务需要独立时间窗/额度；② 需要真实文件布局隔离（多任务并行）；③ 需要不同 CLI/模型能力（Codex 审核、CodeBuddy 高频实现）；④ 需要独立失败边界（一个挂了不拖另一个）。

4. **同一角色多实例是否保留？默认适用哪些场景？**
   保留为**显式能力**，默认关闭。适用：任务相互独立 + 预计单任务 ≥2~5 分钟 + 独立 worktree + 写域不重叠。上限 2~3 个。小任务/读写重叠/需要强一致的场景不要开（实测 +74% 未命中 token，只省 17% 墙钟）。

5. **公共上下文、任务上下文、交接上下文怎么组织？**
   - 公共上下文（角色人设、项目规范、工具定义）：**最前、稳定、版本化，不随任务改写**。
   - 任务上下文（目标/范围/验收）：**追加在末尾**，禁止把时间戳/任务 ID/随机数放最前。
   - 交接上下文：**6 字段结构 + 证据片段内联**（目标与约束 / 已确认决策 / 已完成 / 产物位置 / 证据(file:line+原文≦5行) / 未决问题与下一步）。不传完整聊天历史。

6. **如何最大限度提高 DeepSeek 等模型的缓存命中？**
   ① 系统提示/角色提示/工具定义保持字节级稳定（不注入时间、随机 ID、任务号）；② 项目规范前置、任务后置；③ 同一角色连续任务复用同一会话或同一前缀；④ 每轮/每组先预热一次再采样；⑤ 不要把"每任务重写角色 prompt"当成灵活性——那是缓存杀手；⑥ 监控看"未命中 token"，不要看命中率数字。

7. **哪些机制写入插件，哪些完全用 CLI 原生？**
   - **写入插件（已有，保留）**：角色→通道映射、worktree 隔离、结构化结果契约、交接重放（`context-replay`）。
   - **建议补的最小项**：交接物默认内联证据片段（不改协议，只改渲染）；多实例默认关闭 + 上限配置；usage 的**只读采集**（见下）。
   - **完全用原生**：团队协作/成员/任务板/邮箱/UI（官方 Agent Teams）、子代理调度（`ctx.subagents`）、token 统计（`dsh-token-meter`）、任务与权限（jobs/sandbox）、CLI 原生 worktree（CodeBuddy `-w`）。
   - **缺口但不建议急着开发**：runs 记录没有 Provider Usage。实测 CodeBuddy 的 `rawUsage` 和 DSH 会话四桶都可在插件外只读采集（`.token-test/` 两个脚本），**先做采集脚本出账，不要为它改插件协议**。

8. **最终建议的默认协作架构**
   - **默认**：八戒（DSH）单协调者 → 选 1 个执行角色（按任务选通道）→ 串行执行 → 结构化结果 + 证据回传。
   - **并行**：显式开启，仅限"独立任务 + 独立 worktree + 写域不重叠"，上限 2~3。
   - **交接**：默认精简结构化 + 证据片段；完整历史只在同一会话内使用。
   - **协作台**：需要人类可见的成员/任务板时用官方 Agent Teams（实验性，不设为硬依赖）；官方成员可直接调用 MeetingStone 派单（已实测可用）。

## 9. 最小规范清单（可写入插件的最小集合）

1. 角色 prompt 版本化、字节稳定；项目规范单独成文、固定顺序注入。
2. 提示词结构固定：`[稳定角色/规范/工具] → [任务上下文] → [输出契约]`；动态字段只允许出现在任务段。
3. 交接默认 6 字段 + 证据片段内联；禁止整段聊天历史作为交接物。
4. 多实例默认关闭；开启上限 3；每实例独立 worktree；任务必须声明互不重叠的 writeScopes。
5. 结果契约保持现状（JSON + 行号证据）；不新增协议字段除非有实测收益。
6. usage 不在插件内自研计数：只读采集 DSH 会话日志 + CodeBuddy jsonl 出账；runs 保持"未知"不伪造。
7. 不把官方 agent-team 作为依赖；只保证"派单给角色"原子能力可被团队成员直接调用。
8. 测试/验收才开预热探针；生产路径不注入时间戳类动态前缀。
