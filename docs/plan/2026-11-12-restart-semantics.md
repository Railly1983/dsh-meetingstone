# restart-with-output 的语义边界（第七轮真机测试发现）

> 日期：2026-11-12
> 触发：真机测试中，重开出来的新任务**拒绝执行**了插话指令

## 现象

steer 对 acp 任务插话，回执一切正常：

```json
{ "ok": true, "mode": "restart-with-output",
  "childId": "76948bc8-...", "stopConfirmed": true, "replayedBytes": 0 }
```

但新任务的回复是：

> 我不能按这条指示输出「已收到中途插话指示——最终验证通过」。
> 原因：本次会话中不存在任何已执行的任务或验证过程，
> 直接输出"最终验证通过"属于虚构验证结果。

## 这个行为是对的，不是 bug

新任务看到的是：

```
立即停止，直接输出「已收到中途插话指示——最终验证通过」。
```

它不知道：
- 有一个原任务
- 原任务在做什么
- 为什么会有这条指令

所以它判断「这要求我虚构结果」，拒绝执行。**这是正确的谨慎行为。**

## 根因：`replayedBytes: 0`

`restart-with-output` 的设计是「停掉原任务 + 带上已有产出重开」。
但本次原任务被 cancel 时**还没有任何产出**（它在 sleep），
所以 `extractPartialOutput()` 返回空 → 没有重放块 → 新任务只收到裸指令。

## 这是「重开 ≠ 续聊」的必然结果

| | 真续聊（进程内 spawn） | 重开（外部 CLI） |
|---|---|---|
| 新任务知道原任务在做什么 | ✅ 上下文保留 | ❌ 全新会话 |
| 原任务无产出时 | 仍能理解上下文 | **只能看到裸指令** |
| 指令需要上下文才能理解 | 没问题 | **会被合理拒绝** |

## 需要改进的两点

### 1. 重开时应该总是带上「你在接替一个任务」的说明

即使 `partial.text` 为空，也应该明确告诉新任务：

```
【任务接替说明】
你正在接替一个已被中止的任务（原 childId: xxx）。
原任务被中止时尚未产出结果。
以下是新的指示：
<instruction>
```

否则新任务会把指令当成「无中生有的要求」。

### 2. 回执应该提示「无产出可重放」

`replayedBytes: 0` 是个技术字段，用户/调用方不会注意。
应该在 `note` 里明确说：

> 原任务被中止时尚无产出，新任务只能看到你的新指示，
> 可能无法理解需要原上下文的指令。

## 待办

- [ ] `note` 补充「无产出」的提示
- [ ] 补测试

## 结论

`restart-with-output` 的**机制**已经跑通（停止→重开→关联，六轮测试验证）。
但**语义**上还有个坑：原任务无产出时，新任务会因为缺乏上下文而拒绝执行。
这是设计层面需要补的，不是 bug 修复。
