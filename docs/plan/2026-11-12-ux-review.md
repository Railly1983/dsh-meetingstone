## 1. CLI 开关与角色开关是否分离

**结论：已分离，符合预期。** 两套状态互相独立，点击角色开关不改动健康字段，CLI 卡片不显示版本号/额度。

### 1.1 两套独立状态
- CLI 开关状态来自 `cliPreferences`（用户显式偏好，`src/cli/preferences.js:82` `preferenceOf`）叠加 `preflight` 派生（`deriveCliState` `preferences.js:142`），`enabled` 仅由「非关闭且 preflight ready」决定，与角色状态毫无耦合。
- 角色状态来自 `src/gui/state-model.js` 的三字段派生：`userPreference`（仅 enabled）/ `readiness` / `quota`，三色 `deriveRoleColor`（`state-model.js:264-273`）只由这三个字段求矩阵，不引用 CLI 偏好。
- Host 把两套状态分别投影：`cliStateView`（`host.js:260-291`）与 `roleView`（`host.js:148-211`），互不写入对方字段。

### 1.2 点击角色开关不改动健康状态
- 角色列表开关 `Switch` 的 `onChange` → `toggleManagerRole`（`client/index.js:2067`）→ 只写 `updateGlobalRole(roleId, { enabled: next === true })`（`client/index.js:2074`）。
- 开关的颜色 `color: asObject(role.state).color`（`client/index.js:1701`）是**只读派生**展示，点击只翻转 `enabled`，不会改写 readiness/quota，更不会把“灰/黄/绿”当成可写控件状态。确认：原生 `Switch` 只回传布尔（`client/index.js:752-755`）。

### 1.3 CLI 卡片不显示版本号/额度
- `CliSwitchRow`（`client/index.js:1294-1349`）只渲染 `row.label` + `Switch`，注释明确「不显示版本/路径/额度/通道/徽章」（`client/index.js:1291`）。
- `cliRowsOf`（`client/index.js:1268-1288`）下发给 UI 的对象只有 `cli/label/userPreference/enabled/ready/blockedReason/manualSteps/retryable`，**不含 version/path/quota**。
- 虽然 Host 的 `cliStateView` 算出了 `version`（`host.js:280`）和 `quota` 概念，但 `CliSwitchRow` 从不渲染它们。✔ 符合「CLI 卡片不展示版本号和额度」。

## 2. 全局默认角色配置

**结论：数据层有 `defaultRoleId`，但设置页没有「设置默认角色」的 UI 入口（缺口）。**

- `defaultRoleId` 在 Host 全局视图被读取（`host.js:444`），在客户端被归一化（`client/index.js:436`）。它是自动路由兜底（`docs/configuration.md:80`，`src/dispatch/routing.js`），确实被消费。
- 但 `renderSection` 的「默认角色配置」区（`client/index.js:1466-1488`）只渲染：模板名 + 一句说明 + 角色数量 + 「管理角色」按钮。**没有任何下拉/控件让用户选择默认角色。**
- 字典里 `defaultRole: '默认角色'`（`client/index.js:931`）定义了却**从未被 `t('defaultRole')` 调用**（全文件无引用）。
- 即：区标题叫「默认角色配置」，实质只是「全局角色库管理」，默认角色本身不可在 UI 配置。这与数据模型不一致，是一个真实的 UX 缺口（不是纯文案问题）。

## 3. 项目级继承与覆盖

**结论：存在一处需要澄清的代码/契约冲突。代码并未让「项目级 roleOverrides 失效」——配置层仍在解析并应用它；UI 没有写出“项目可覆盖”的字面文案，但残留了「项目」来源标签，且有一处过时的「会话覆盖记录」提示。**

- 契约/决策声称失效：`docs/gui-0.2.0.md:809`「用户 2026-11-12 决定：本插件**只保留全局角色设定**，取消项目级/会话级角色配置」；`docs/release/0.1.0-alpha.6-checklist.md:13`「B3b｜角色配置收敛为全局单层，项目级 roleOverrides 失效」。
- 但代码仍完整支持项目级覆盖：
  - `src/session/config.js:569-619` 仍然读取 `projectConfig.roleOverrides` 与项目级 `roles`，并为每个字段计算 `layer='project'`（`config.js:590-611`）。
  - `src/project/config-file.js:160-178` 与 `src/project/write.js:150-180` 仍解析/写入 `roleOverrides`。
  - 因此：若用户在 `.meetingstone.json` 写了 `roleOverrides`，它**仍会生效并覆盖全局**——所谓“失效”并未在解析层落地。
- UI 侧：
  - 没有字面“项目可覆盖”文案。
  - 但 `SOURCE_LAYERS` 仍含 `'project'`（`client/index.js:537`），`sourceMeta` 把 `'project'` 映射成标签「项目」（`client/index.js:2299` + 字典 `sourceProject: '项目'` `client/index.js:999`）。因为配置层仍会算出 `project` 来源，角色字段的「来源」标签**仍可能显示「项目」**——这与“只有全局角色”的叙事矛盾。
  - `confirmDeleteRole`（`client/index.js:974`）写「已有**会话**的覆盖记录不会被改写（可能指向已删角色）」，但同一面板自己的 `globalRolesNote`（`client/index.js:950`）声称「B3 起不再有会话级临时覆盖」。两处自相矛盾：删除提示还在引用已（按决策）不存在的会话覆盖记录。
- 小结：UI 没有写“项目可覆盖”，但 (a) 配置代码仍应用项目覆盖、(b) UI 残留「项目」来源标签、(c) 删除提示引用会话覆盖记录——这三条与“B3 只有全局角色”的契约不一致，需在代码或文案上择一收口。

## 4. 模型、思考强度与角色提示词配置

**结论：符合预期。「角色设定」是单一字段（description+prompt 合并）；取值链路清晰，且只暴露 CLI→模型→思考强度，不再有「通道」用户概念。**

- 编辑器字段来源：`deriveRoleEditorFields`（`state-model.js:380-401`）返回 `setting`（合并）、`cli`、`model`、`effort`（reasoning），以及对应的 options。
  - `setting` 合并逻辑：`role.setting` → 否则 `role.prompt` → 否则 `role.description`（`state-model.js:385-392`）。
- Host 投影同样把 `setting` 作为单一字段（`host.js:185-192`），并保留 `description`/`prompt` 为兼容镜像。
- 客户端详情渲染（`renderRoleDetail`，`client/index.js:2854-2917`）字段顺序：名称 / 简称 / **角色设定（单一 textarea）** / CLI / 模型 / 思考强度。无独立「描述」与「Prompt」两栏。
- 写回：`buildGlobalPatch`（`client/index.js:2642-2678`）只写 `patch.setting = setting`（单一字段，`2653-2656`），不分别写 description/prompt。✔
- 联动：切 CLI 清空模型/强度（`client/index.js:1941-1947`），模型变更清空强度（`2774-2779`、`2804-2808`）；选项只来自能力目录（`detailOptionsOf` `2620-2635`），目录没有就显示「不支持」并置灰（`2789-2852`）。不伪造能力。✔

## 5. CLI 检测与错误提示指引

**结论：基本符合预期。CLI 未安装/检测失败时，给出一行摘要 + 人工步骤 + 重新检测；错误是一行而非大段。**

- 失败呈现：`CliSwitchRow` 在 `failures[cli]` 存在时追加块（`client/index.js:1311-1347`）：
  - 摘要行 `role='status'`，`whiteSpace:'nowrap' + ellipsis`（`client/index.js:1321-1326`），`title` 里放完整 `[code] message`，即“一行摘要、详情在 tooltip”。✔
  - 人工步骤：`manualSteps` 以「人工步骤：…」展示（`client/index.js:1331`）。
  - 可操作按钮：「重新检测」（非 `retryable===false` 时显示，`client/index.js:1335-1341`）。
- 人工步骤内容真实可操作：`src/cli/preflight.js:46-76` 的 `PREFLIGHT_MANUAL_STEPS` 覆盖未安装/需登录/宿主 provider 未启用/权限/路径/启动失败/证据缺失，每条都是“做 X，然后点重新检测”，且明确“本项目不代装/不代登录”。✔
- 一处可优化（非缺陷）：人工步骤**仅在用户尝试开启并失败后出现**。若 CLI 从未被点过，行内只有关闭的开关、没有前置的“未安装怎么办”提示；用户需先误点一次才看到指引。可考虑在 `ready!=='ready'` 且非用户主动关闭时，也默认展示一行摘要 + 重新检测（与失败态共用渲染）。

## 发现的不一致（代码与契约/文案冲突）

1. **「项目级 roleOverrides 已失效」与代码冲突**：决策文档（`gui-0.2.0.md:809`、alpha.6-checklist:13）称项目/会话级角色覆盖已取消，但 `src/session/config.js:569-619`、`src/project/config-file.js:160-178`、`src/project/write.js:150-180` 仍在解析并应用项目级 `roleOverrides`。配置层并未失效。
2. **`confirmDeleteRole` 与 `globalRolesNote` 自相矛盾**：删除提示引用“会话的覆盖记录”（`client/index.js:974`），而同面板称“B3 起不再有会话级临时覆盖”（`client/index.js:950`）。
3. **「默认角色配置」标题名实不符（第 2、6 项）**：`defaultRoleId` 有数据、有消费，但设置页无 UI 入口；字典 `defaultRole` 键从未渲染。
4. **「项目」来源标签残留**：UI 仍可能显示「项目」来源（`SOURCE_LAYERS`/`sourceProject`），与“只有全局角色”的叙事不符。
5. **CLI 区行数与验收清单不一致（轻微）**：D1 验收期望 CLI 区含「DeepSeek Harness 等行」（`docs/plan/verify/2026-11-13-d1-user-checklist.md:12`），但 `cliRowsOf` 只渲染 `codex/codebuddy/claude` 三个外部 CLI（`client/index.js:243,1268`），不包含 dsh 宿主行；dsh 只在能力目录与 `refreshCli('dsh')` 分支处理。

## 最值得改的 3 件事（排序）

1. **收口「项目/会话覆盖」的真相**（影响正确性，最高优先）：在代码或文案上二选一——要么让 `src/session/config.js` / `src/project/*` 真正忽略项目级 `roleOverrides`（落实 B3b），要么把决策文档与 UI 文案（`globalRolesNote`、`confirmDeleteRole`、移除「项目」来源标签）校准为“项目覆盖仍生效但不在 UI 编辑”。当前状态是代码与契约各说各话，最危险。
2. **补齐「默认角色」配置入口**（影响核心功能可用性）：在「默认角色配置」区加一个 `defaultRoleId` 下拉（数据已就绪、`host.js:444` 已投影），或把区标题改为「全局角色库」以避免误导。
3. **清理死代码与死字典**（影响可维护性、符合极简）：删除约 50 条未渲染的 i18n 串、移除生产不可达的 `showScope`/会话全局切换分支、精简 `templateDesc` 与 `globalRolesNote`，并校准 `confirmDeleteRole` 的过时文案。
