# P0-A 真实 A/B 对照实测（工具回执字节 / Token）

> 日期：2026-11-11
> 角色：沙僧
> 依据：`docs/reference/efficiency-v1.0.md` §7.2（A/B 方法）、§9（Token 口径）、§11（验收）
> 前置：`docs/plan/2026-11-11-tool-output-baseline.md`（固定合成样本基线）
> 性质：**只读实测**。未改代码、未 commit、未安装/重启/改 profile。

## 0. 结论摘要

| 工具 | 真实样本 | 旧（B 组）p50 | 新（A 组）p50 | 中位降幅 | 判定 |
| --- | --- | ---: | ---: | ---: | --- |
| `dispatch` | 76 旧 / 26 新（真实回执） | 882 B | 251 B | **-71.5%** | 接近合成基线，可复现 |
| `get_task` | 67 条真实 run 记录配对回放 | 4762 B | 3202 B | **-12.2%** | 远低于合成基线的 -78.5%，且 5/67 反向变慢 |
| `list_roles` | 真实 6 角色配置 + 6 条旧版全量真实回执 | 2102 B | 699 B | **-66.7%** | 与合成基线 -70.9% 同量级 |

三条硬结论：

1. **`dispatch` / `list_roles` 的瘦身在真实派单里成立**，中位降幅 71.5% / 66.7%；但合成基线给旧回执塞了约 4 KB 的长人设 + Context Pack，真实旧回执的 `role`（含 `prompt`）只有约 500–700 B，所以 95.0% 是**上界**，不能对外引用。
2. **`get_task` 默认摘要不是普遍降 78.5%**：真实数据总量降 29.8%，中位仅 12.2%，大结果（≥1.5 KiB）中位 37.0%，且有 5 条**反向膨胀**（最多 +34.2%）。原因是回执带 48–50 个结构化字段的固定开销，外加 `protectedSections` 把截断中段找回。
3. **Token 不能精确归属到工具**：Provider Usage 只有会话级字段（真实可读），日志里没有 per-tool usage。用同会话「工具 schema 字节 ÷ toolsTokens」实测得到 **4.14 B/token** 只能作估算折算：`dispatch` ≈152 tok/次、`get_task` ≈510 tok/次、`list_roles` ≈339 tok/次；但 98.7% 的输入是 cache read，实际计费节省会明显小于此数，**不得当成已实现节省**。

## 1. 方法

### 1.1 三类数据源（互补，不混用口径）

| 代号 | 数据源 | 样本量 | 用来回答 |
| --- | --- | --- | --- |
| R1 | DSH 宿主会话日志 `~/.dsh/sessions/--D-MeetingStone--/*/session.v4.jsonl.zstd` 的 `tool/result` 文本 | **287 条真实回执**（3 个会话） | 真实派单实际返回了什么、模型实际看到多少字节 |
| R2 | `.meetingstone/runs/*.json` 真实运行记录 **67 条**，经真实 `registerTools()` 重放 | 67 对（默认 vs `full:true`） | 同一记录两种投影的**配对**对照，消除任务难度差异 |
| R3 | `node scripts/measure-tool-output.mjs --json` | 3 组固定合成样本 | 与既有基线对齐、检查偏差 |

R1 的提取方式：DSH 日志为多帧 zstd，用宿主编带的 Node 24（`zlib.zstdDecompressSync`）逐帧解压；按 `tool/call` 的 `callId` 关联 `tool/result.message.toolCallId`，取 `content[].text` 拼接后的 UTF-8 字节数。**字节口径 = 模型可见的回执文本**，包含宿主对超长工具结果的中段裁剪（见 §6 局限）。

R2 的重放方式：假 `ctx` + 假 dispatcher（`getTask → {status:"unknown"}`）+ `loadPersistedRun` 返回真实记录，调用**当前仓库真实的** `get_task.execute`（`src/dsh/register.js:822`），分别取默认与 `full:true`。同一记录、同一代码，只有 `full` 一个变量。

R3 复现命令、合成样本构造见 `docs/plan/2026-11-11-tool-output-baseline.md`。

### 1.2 分组定义

- **A 组（新机制）**：`get_task` 默认摘要、`dispatch` 紧凑回执、`list_roles` 默认紧凑。
- **B 组（旧机制等价）**：
  - `dispatch`：真实历史上「返回完整 role 对象」的旧回执（不是构造的）；
  - `get_task`：`full:true`（真实日志中 **0 次** `full:true` 调用，只能由 R2 配对重放得到）；
  - `list_roles`：旧版默认全量详情（真实日志 6 条，`args` 均为 `{}`，不是显式 `verbose:true`），另有 R2 用当前工具 `verbose:true` 对真实配置重放。

### 1.3 新旧判定（按回执形状，不按提交时间）

| 工具 | 旧形状 | 新形状 |
| --- | --- | --- |
| `dispatch` | 顶层含 `role` 对象（roleId/name/description/channel/source/permissionPreset…） | 顶层 `roleId` + `roleName` + `isolation` |
| `get_task` | 只有 `output`（全文），无 `resultBytes` | `resultOmitted:true` + `summary`，或 `result` 首尾摘要 + `resultBytes` |
| `list_roles` | 角色含 `description/channel/channelId/model/hasPrompt` | 当前默认仅 `roleId/name/aliases/enabled/availability`（5 字段）；11-10 上午的旧版曾多 `permissionPreset/channel/source`（8 字段） |

按形状判定而非按 commit 时间：实测切换点在 **2026-11-11T03:32–03:45Z**（11:32–11:45 +08:00），比提交时间 02:17Z 晚约 1–1.5 小时，说明部署有滞后。

> 版本细节：`dispatch` 旧回执的 `role` 对象在 66 条可解析样本中，55 条含 `prompt`，11 条不含；`prompt` 字节数 p50 = 246 B、max = 279 B（不是合成样本的 4 KB 长人设）。`list_roles` 的版本窗口**非单调**：11-10 上午是 8 字段紧凑版，11-10 下午到 11-11 凌晨默认回 12 字段全量，11-11 03:45Z 起才是当前 5 字段默认。因此 `list_roles` 的 B 组取「旧版默认全量」，不假设它等于 `verbose:true`。

## 4. Token 可得性

### 4.1 能读到的 Provider Usage（真实字段）

来源：`~/.dsh/storages/session_projcache/sessions/<id>.json` → `record.rows.tokenUsage.val` / `contextBreakdown.val`。

| 会话 | uncachedInputTokens | outputTokens | cacheReadTokens | cacheWriteTokens |
| --- | ---: | ---: | ---: | ---: |
| `f8b00633`（旧） | 825,116 | 325,173 | 152,402,688 | 0 |
| `cc5a771a`（旧） | 2,284,395 | 459,803 | 294,994,560 | 0 |
| `417e6b6a`（跨版本） | 7,424,344 | 850,194 | 569,230,848 | 0 |
| `274cbe89`（新） | 91,466 | 38,154 | 4,416,768 | 0 |

字段名与值都是真实计费口径（`inputTokens`/`outputTokens`/`cache_read_input_tokens`/`cache_creation_input_tokens` 的宿主映射），但**粒度是会话，不是工具调用**。

### 4.2 折算系数（实测，不是通用 tokenizer）

同一会话 `417e6b6a`：

- `request/header.tools` 的 JSON = **43,582 B**；
- 同会话 `contextBreakdown.breakdown.toolsTokens` = **10,517 tokens**；
- 比值 = **4.14 B/token**（该 provider `deepseek-flash`、该内容形态）。

按此折算（**估算**）：

| 项 | 节省字节 | 估算 Token | 说明 |
| --- | ---: | ---: | --- |
| `dispatch` 每次 | 631 | ~152 | p50 差额 |
| `get_task` 67 次合计 | 141,548 | ~34,158 | 配对回放累计 |
| `get_task` 每次 | 2,113 | ~510 | 平均值 |
| `list_roles` 每次 | 1,403 | ~339 | 真实 6 角色配置 |

### 4.3 边界（必须写「未知」的部分）

- **per-tool Provider Usage：未知**。会话日志只有 `assistant/message` 的模型名与 provider，没有 per-call usage 字段；宿主 cache 的 `tokenUsage` 也是会话累计。
- **真实计费节省：未知**。`417e6b6a` 的 input 中 98.7% 是 cache read（569,230,848 / (569,230,848 + 7,424,344)），回执字节减少主要影响**首次未缓存读**与上下文压力，不等于账单线性下降。
- **跨 provider 不可外推**：4.14 B/token 是 deepseek-flash 的 JSON 实测；CJK 正文、其他 tokenizer 会偏离。表中 Token 列一律标「估算」。
- 合成脚本的 `approxTokens`（`ceil(max(bytes/4, CJK 数))`）与本次 4.14 B/token 不是同一口径，不能互相印证。

## 5. 结论

1. `dispatch` 紧凑回执在真实派单中稳定成立：p50 882 → 251 B（-71.5%），26 条新回执全部落在 249–258 B，方差极小。**可写入验收证据**，但对外只能说 70% 量级，不能说 95%。
2. `list_roles` 紧凑在真实 6 角色配置下 -66.7%，与合成基线一致，**可写入验收证据**。
3. `get_task` 默认摘要**只在长结果上明显**：≥1.5 KiB 时中位 -37%，全量合计 -29.8%；中位仅 -12.2%，且有 5/67 反向膨胀。要满足「默认摘要显著瘦身」，需要先削减结构化字段固定开销（48–50 个键）与 `protectedSections` 的重复找回，否则不能宣称 -78.5%。
4. Token 维度只能给**估算折算**与会话级真实 Usage；per-tool 归属和真实账单节省均为**未知**。

## 6. 局限

- **不是双臂对照实验**：A/B 来自同一批真实任务的跨版本回执 + 同记录重放，不是「同任务同时跑两套插件」。`dispatch` 的新旧样本任务不同，只能比分布不能比配对。
- **`get_task full:true` 无真实样本**：真实日志 123 次调用**全部没传 `full`**，B 组由 R2 重放提供；重放走的是当前代码路径，与历史旧版字段集不完全相同（旧版只有 `output`，重放会带 `recordPath` 等新元数据）。
- **宿主中段裁剪**：6/123 条 `get_task` 回执被宿主截断（保留前 4 KiB + 尾部一段，插入 `[... tool result middle pruned ...]`），R1 记的是模型实际看到的字节，不是工具原始输出；这会让旧版长结果看起来比真实更小，属于**保守偏差**。
- **样本偏斜**：`417e6b6a` 是同一项目、同一模型（deepseek-flash）的长会话；`f8b00633`/`cc5a771a` 角色少、结果短。无审查/调研/数据分析类任务的分层。
- **快照漂移**：`417e6b6a` 在采集期间仍在写入（283 → 287 条），复跑数字会有小幅变化；`p0a-ab-receipts.slim.json` 固化了本次快照。
- **`get_task` 结果字段演化**：67 条记录跨多个版本（有的无 `summary`，有的 `protectedSections` 为空），配对回放用的是**当前**代码，因此反映的是「当前机制对历史数据的投影」，不是「历史版本当时的字节」。
