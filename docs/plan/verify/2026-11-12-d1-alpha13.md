## 二、第一组：模型刷新（本次修复重点）逐条结论

> 证据全部来自脚本真实运行 + 源码静态确认。脚本输出见文末「复现命令」。

### 1. 角色编辑器 CLI 下拉数量 —— ⚠️ 与任务预期不符，实际 4 个

| 项 | 任务预期 | 实际（代码+实测） |
| --- | --- | --- |
| CLI 下拉 | 3 个：DeepSeek Harness / CodeBuddy / Codex | **4 个**：DeepSeek Harness / **Claude Code** / Codex / CodeBuddy |

- 证据：`src/cli/capabilities.js:26` `CLI_IDS = ['dsh','claude','codex','codebuddy']`（固定 4 个）；`src/client/index.js:337` 同样 4 个；`src/client/index.js:2566` `capabilitiesOf` 末尾 `return CLI_IDS.map(...)`，永远补满 4 个。
- 实测脚本：`CLI 数量 = 4 → DeepSeek Harness / Claude Code / Codex / CodeBuddy`。
- **结论**：本次修复让 `dsh` 不再被跳过（原 D1-B1 成因 A 的 enum 缺失 + 成因 B 的 `channelsToCatalog` 跳过），**4 个 CLI 全部出现**。任务的「应 3 个」与实际代码不符——漏算了 **Claude Code**（其模型来自静态表 sonnet/opus/fable，见下）。这是任务预期描述的偏差，不是缺陷。

### 2. 选 DeepSeek Harness → 模型含 `deepseek-v4.1-flash` —— ✅ 通过

- 实测：`dsh.models = [deepseek-v4.1-flash]`，`source=config`。
- 根因：`channelsToCatalog` 现在读 `channel.llmModel`（capabilities.js:346 `const model = asString(channel.llmModel) || asString(channel.model)`），in-process 通道 `ch-inprocess.llmModel=deepseek-v4.1-flash` 被正确纳入。

### 3. 选 CodeBuddy → 模型含 `kimi-k3.1-pro / hy4free / glm-5.3-flash / hy3` —— ✅ 通过

- 实测：`codebuddy.models = [kimi-k3.1-pro, hy4free, glm-5.3-flash, hy3]`，均 `source=config`。
- 来源：4 个 `acp-cli` 通道的 `model` 字段 + provider 行 `--model` 声明，经 `mergeCatalogs`/`mergeRoleBoundModels` 合并。

### 4. 选 Codex → 模型含 `gpt-6-astra / gpt-6.1-sol` —— ✅ 通过

- 实测：`codex.models = [gpt-6-astra, gpt-6.1-sol]`，`source=config`。

### 5. 选模型后思考强度有值（至少 DSH 与 CodeBuddy 有 `high`）—— ✅ 通过

- 实测：`dsh.strengths = [high]`（来自 `ch-inprocess.reasoning=high`）；`codebuddy.strengths = [high]`（各 acp-cli 通道 `reasoning=high`）；`claude.strengths = [low,medium,high,xhigh,max]`（静态表）；`codex.strengths = []`（空，见第三组 item 8）。
- 注：任务只要求 DSH + CodeBuddy 有 `high`，二者均满足。

### 6. 来源标注正确（角色绑定模型应标「来自角色」，不是伪装成探测结果）—— ⚠️ 部分（负向通过 / 正向未达成）

- **负向要求「不是伪装成探测结果」：通过**。所有模型 `source=config`（或 `static`/`unknown`），**没有**被标成 `discovered`（动态）。角色绑定的 `kimi-k3.1-pro`（唐僧）确实出现了，且没有假装成探测结果。
- **正向要求「应标为来自角色」：未达成（代码层缺口）**。`mergeRoleBoundModels` 在内部目录给这些模型打了 `sources: ['channel','role']`（capabilities.js:430、:437），但：
  - `buildCatalogEntry`（capabilities.js:813-822）构造最终模型时**丢弃 `sources` 数组**，统一写 `source: CAPABILITY_SOURCES.CONFIG`；
  - GUI 渲染只取 `item.source`（client/index.js:2815、:2846 → `${item.label} · ${sourceText(item.source)}`，即 `kimi-k3.1-pro · 配置`）。
  - 结果：角色绑定模型与通道声明模型在 UI 上**都显示「配置」**，无法区分「来自角色」还是「来自通道配置」。
- **结论**：核心诉求（角色绑定模型可见、不伪装成探测）已达成；但「标为来自角色」的精细标注在 `buildCatalogEntry` 处丢失，UI 无法呈现「· 角色」。属代码层取舍/缺口，**非功能回归**（之前这些模型根本不显示）。建议二选一：①接受「配置」即足够诚实（因其不是 discovered）；②在 `buildCatalogEntry` 保留 `sources` 并让 GUI 优先渲染 `role` 来源。

## 四、第三组：已知问题核实

### 7. 黄色状态不可达 —— ✅ 判断仍成立（非回归，V1 已知设计取舍）

- 现状：`src/gui/host.js:156-160` 调 `deriveRoleView(role, { subagents, availability: roleAvailability(role, ctx), sources })` —— **未传 `quota`**。
- `deriveQuota`（state-model.js:247-256）在无 `ctx.quota` 时：无 rejected source 且 quota 非合法值 → 若 `billingMode` 非 pay-as-you-go 则返回 `UNKNOWN`。
- 本机 6 角色均非 pay-as-you-go → `quota=unknown` → `deriveRoleColor`（state-model.js:264-273）只走 green/gray 分支，**黄色永远不可达**。
- **结论**：alpha.6 报告「D1-M3 黄色生产不可达」的判断**仍成立**，且非本次回归，属 V1 无额度数据源的已知取舍。需用户目视确认真机无黄（正常，非缺陷）。

### 8. codex 思考强度为空 —— ✅ 确认（设计使然，非缺陷/非回归）

- 现状：profile `ch-codex-astra` / `ch-codex-sol` 两个 codex 通道**均无 `reasoning` 字段**（cordis.patch.yml:113-122）；provider 行 `subagent-codex` / `subagent-codex-sol` 也无 `--effort`。
- `channelsToCatalog` 中 `effort = asString(channel.reasoning)` 对 codex 为空 → `codex.strengths = []`。
- 实测脚本：`codex.strengths = (空)`。
- **影响**：Codex 强度下拉为空、置灰「不支持 · 当前 CLI 没有可选推理强度」。这是**设计使然**——codex 强度需真实启动 `codex app-server model/list` 动态发现 `supportedReasoningEfforts`（capabilities.js `probeCodexModels`），按纪律不派真实 codex，故静态/契约层为空。非本次修复的回归，也非缺陷。
- **结论**：确认 item 8 判断成立；属环境/设计限制，不影响 D1 通过裁定。
